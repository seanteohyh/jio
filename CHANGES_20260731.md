## ⚠️ Standing rule — README is part of the change, not a follow-up

**Every commit that adds, removes or changes a feature updates `README.md` in
the same commit.** Not afterwards, not "when there's time."

This isn't housekeeping. The last commit is the proof: it shipped eight
migrations and seven new test files, and the README still describes Reco — a
feature that commit deleted — still lists push notifications and rating views
under "Not built yet" when both had just shipped, and still claims a test
count that stopped being true. The README is the only document explaining what
Jio *is*. Once it disagrees with the code, its trustworthiness goes to zero
and there's no cheap way to earn it back.

A change isn't done until all of these are true:

- [ ] Feature table reflects what exists
- [ ] Scoring-weights table matches `recommendConfig.ts`
- [ ] Migration count matches `supabase/migrations/`
- [ ] Test count and test-file table match `tests/`
- [ ] "Not built yet" no longer lists anything that now exists
- [ ] Env-var table covers anything new — **and it's set in Vercel too**
- [ ] `SETUP.md` still accurate if setup steps changed

**Which README sections each item below will touch:**

| Item | Update in README |
|---|---|
| §1 office | Env-var table; the "walking distance" claims |
| §2 nav | Feature table (Suggest is now reached from Places) |
| §3 Home flow | Nothing, if it's purely a routing fix |
| §4 invite picker | Feature table (Jios/Kakis rows); migration count if RLS changes |
| §5 name prompt | Accounts section — the `name` mode walkthrough |
| §6 share link | Env-var table (`NEXT_PUBLIC_SITE_URL`) |

**Consider a `docs/` folder while you're at it.** `CHANGELOG_20260729.md`

## 1. LazadaOne office location — coordinates fixed, derived data stale

**Status 31 Jul: lat/lng updated directly in the Supabase `offices` row.** The
source of truth is correct. Everything computed *from* it is not.

### 1a. Confirm the DB is actually the source of truth — do this first

`.env.local` has `NEXT_PUBLIC_JIO_OFFICE_*` variables. If the app reads office
coordinates from **env** rather than from the `offices` table, the Supabase
edit changes nothing user-facing and the map will still be wrong.

Check which one wins before doing any of the work below. If env is used —
either instead of, or as a fallback to, the DB — update it in `.env.local`
**and in Vercel**, since the deployed site reads Vercel's copy.

Also check `src/app/map/page.tsx` for a separately hardcoded map centre.

### 1b. Invalidate and rebuild `walk_cache`

This is the main remaining job. `walk_cache` (migration 003) stores walking
times computed from the **old** origin, so every row is wrong. Sorting,
filtering and the walk penalty all read it.

1. **Inspect the schema** — `select * from walk_cache limit 5;`. If it keys on
   `office_id`, delete only LazadaOne's rows; if it keys on `place_id` alone,
   the whole table goes.
2. **Delete the stale rows**, don't try to update in place.
3. **Re-run** `npm run seed:walktimes` (`scripts/enrich-walktimes.ts`) with
   `.env.local` pointed at the production Supabase project.

**Delete before re-running.** If the script skips places that already have a
cached time — which is the obvious way to write it — then re-running without
clearing does nothing at all and looks like success. Confirm its behaviour, or
just clear the rows first.

**Expect a visible gap while it runs.** `/places` sorts by walk time with
`NULLS LAST`, so between the delete and the re-run finishing, every place sorts
to the bottom in arbitrary order. Do it at a quiet time, or run it immediately
after the delete.

**Check OneMap is configured.** With `ONEMAP_EMAIL`/`ONEMAP_PASSWORD` set you
get real walking routes; without them it falls back to haversine, which runs
20–30% optimistic in a dense area. If the point of this exercise is accurate
distances, verify OneMap is actually being used rather than silently falling
back. Watch for rate limiting if the place count has grown well past the
original 25 — batch if needed.

### 1c. Re-run place discovery

`/api/cron/discover` sweeps Overpass in a radius around the office. Everything
currently in the database was found around the *old* coordinates, so places
near the real LazadaOne may never have been discovered, and some existing ones
may now be out of walking range.

```bash
curl -H "Authorization: Bearer $CRON_SECRET" \
  https://your-app.vercel.app/api/cron/discover
```

New finds land in the `needs_review` queue as usual.

### 1d. Review the curated seed list

`scripts/manual-seed.json`'s 25 hand-picked places were chosen around Bras
Basah / Bugis for the old location. Depending on how far the office actually
moved, some may now be a long walk. Worth a look once real walk times exist —
the data will tell you which ones to drop.

### 1e. Worth building: invalidate the cache automatically

This will happen again — a second office, a corrected pin, an office move. A
trigger on `offices` that deletes the affected `walk_cache` rows whenever
`lat`/`lng` changes makes the staleness impossible to forget.

Same pattern as migration 021's rating trigger: cheap, always-current, no
schedule. The rebuild still needs running, but at least the app fails honestly
(no cached time) rather than confidently serving wrong numbers.

## 4. The invite picker — kaki groups and a search bar, everywhere

**One component, three surfaces.** The same picker is wrong or missing in
every place it appears, so build it once rather than patching each:

| Surface | State today |
|---|---|
| Jios tab → Start a Jio | Two separate controls: link a kaki group, then invite individuals below. No search. |
| Home → Start a Jio | Stale flow entirely — see §3 |
| Inside an existing Jio (`events/[id]`) | No invite step at all |

### 4a. One unified multi-select search bar

Replace the two stacked controls with a **single search field** that returns
both people and kaki groups, and lets you pick any number of either, freely
mixed. Selected items sit as removable chips.

Practical notes:

- **Label the type.** A group and a person in the same result list need
  visually distinct rows — an icon or a "group · 6 members" caption — or
  picking becomes guesswork.
- **Show what a group expands to** before submit, at least as a count.
  Selecting "LazadaOne Lunch Kakis" and silently inviting eleven people is a
  surprise worth avoiding.
- **Dedupe quietly.** Picking a group and then a person already in it is
  normal, not an error. Resolve to one invite, no warning.
- **Groups: only the kakis you're a member of.** Settled precedent — Lobang
  group-send restricts to kakis the sender actually belongs to.
- Reuse the discriminated-target shape `sendLobang()` uses
  (`{ type: "users", userIds }` / `{ type: "kaki", kakiId }`) so invites,
  lobangs and event creation speak the same language.

### 4b. Resolve what "link a kaki" currently *means* — do this first

**This is the one that could bite.** "Link to group" and "invite people" may
not be two flavours of the same action, and merging them into one picker
assumes they are.

Migration 013's RLS grants event access to **host, kaki member, or explicit
invitee** — three separate paths. So linking a kaki to an event plausibly sets
something like `events.kaki_id` and grants access *dynamically via current
membership*, with no `event_invitees` rows written at all. Inviting a person
writes a row. Those are different mechanisms with different behaviour when
membership later changes.

**DECIDED (31 Jul): do both.** A group chip writes `event_invitees` rows for
the members at submit **and** keeps the kaki reference for display
("Jio with LazadaOne Lunch Kakis"). Exactly what migration 019 chose for
lobangs, so the two features stay consistent.

What this means in practice:

- **The invitee list is fixed at submit time.** Someone joining the kaki
  tomorrow is *not* retroactively part of today's Jio. Someone leaving stays
  invited. That's the intended behaviour, not a gap.
- **`kaki_id` becomes display provenance only** — same role it plays on
  `lobangs`. It should stop being an access-granting path.
- **Therefore check migration 013's RLS.** If the "kaki member" branch
  currently grants event access by live membership, it now overlaps with the
  invitee rows and gives a second, looser path in. Decide whether that branch
  should be narrowed once invitees are always written — otherwise the
  snapshot guarantee is real in the data and untrue in practice.

Still worth reading the existing "link to group" control first to see which
mechanism it uses today, since that determines whether this is an extension or
a change of behaviour for Jios already created.

### 4c. Make the search server-side

**Check the endpoint before building the UI.** `api/users/route.ts` is ~450
bytes, which strongly suggests it returns every user with no filtering. A
client-side filter over that response works fine at team scale and becomes the
wrong answer quietly — the list keeps rendering, just slower and heavier, with
no obvious failure point to catch it. Add a query param while you're in there.

The unified bar needs to search two sources at once, so decide whether that's
one endpoint returning a merged typed list, or two calls the client merges.
One endpoint is easier to paginate sensibly later.

### Where it lands

- `src/app/events/new/page.tsx` — extract the existing invite UI into a shared
  component, then extend it
- `src/app/events/[id]/page.tsx` — mount the same component
- `api/events/[id]/invitees` — extend to accept a kaki target
- `api/users/route.ts` — server-side search

**Decisions still open for the in-event case**

- Can invitees be *removed*, or only added?
- Should late invitees vote on an event already mid-vote? (Probably yes —
  Borda scales partial ballots by the voter's own ballot length, so a late
  voter ranking three options doesn't outweigh someone who ranked six. Worth
  confirming that's the actual behaviour.)
- Late invitees get no notification unless push fires — check whether
  migration 025 covers "you've been added to a Jio."

**Decisions to make**

- Adding a kaki whose members are already partly invited — dedupe silently, or
  show what changed?
- Can invitees be *removed*, or only added?
- Should late invitees be able to vote on an event that's already mid-vote?
  (Probably yes, given Borda scales partial ballots by the voter's own ballot
  length — a late voter ranking three options doesn't get more influence than
  someone who ranked all six. Worth confirming that's actually the behaviour.)
- Anyone invited late gets no notification unless push fires — check whether
  migration 025's push covers "you've been added to a Jio."

## 5. New-user flow asks for the name twice

**Symptom:** open the app fresh → sign-in screen asks for your name → submit →
lands on `/welcome`, which asks for your name *again* plus office. Should be
one screen, shown immediately, no second confirmation.

**Why this happens.** Two features were built independently and now overlap:

- **Name-mode auth** (`nameAuth` adapter, `src/app/login/page.tsx`) — one name
  field, creates a Supabase anonymous session
- **Onboarding** (migration `020_onboarding.sql`, added 30 Jul) — a `/welcome`
  screen capturing name/nickname, gated on `profiles.onboarded_at IS NULL`

The onboarding design assumed users arrive without a name already collected.
In name-mode they always arrive *with* one, so the gate fires on every new
signup and asks a question that was just answered.

**The likely one-line-ish fix:** `api/auth/signin` creates the profile but
probably never sets `onboarded_at`, leaving it null — which is exactly the
condition that triggers the `/welcome` redirect. Setting it at signin time may
resolve this without touching the UI at all. **Check this first** before
planning anything larger.

**One real constraint to design around.** You cannot skip sign-in entirely and
show `/welcome` first: writing a display name or `onboarded_at` to `profiles`
requires `auth.uid()`, which requires the anonymous session to already exist.
Whatever the single screen looks like, submitting it must create the session
*before* it writes the profile. This isn't a blocker — it's one screen doing
two sequential things — but it rules out "just make `/welcome` the landing
page."

**Note the office field carries no input.** Per the onboarding decision, office
is a locked field reading "LazadaOne" with a pilot-only caption — not a picker.
So it's informational, and folding it into the sign-in screen as a caption
costs nothing.

**Which screen survives?** Worth deciding deliberately:

1. **Keep `/login`, delete `/welcome`.** Add the office caption to the sign-in
   screen and set `onboarded_at` on signin. Fewest moving parts. `/welcome`
   would only ever be reachable by an existing user with a null
   `onboarded_at` — which the migration's backfill should have prevented.
2. **Keep `/welcome`, make it do the sign-in.** `/login` redirects to it in
   name-mode. More churn, but leaves a clean home if onboarding ever grows
   past one field.

Option 1 unless you expect onboarding to expand. Note that `/login` still has
to exist for `email` mode, so deleting it isn't on the table either way.

**Check the other two auth modes** before committing: `demo` mode has no
sign-in at all, and `email` mode's magic-link flow is a genuinely separate
arrival path where a `/welcome` step may still be wanted. Whatever changes
here shouldn't assume name-mode is the only one.

## 6. Share this Jio — move it up, and give a real link

Two problems on `src/app/events/[id]/page.tsx` (22 KB, so the share block is
buried a long way down).

### 6a. Position

Sharing is the *point* of creating a Jio — nobody makes one to look at it
alone. It shouldn't be the last thing on a long page, below the options list
and the vote state.

Put it near the top, at least while the event is open and thinly attended.
Worth considering a stronger treatment right after creation specifically —
landing on a freshly-made Jio with the share link as the primary call to
action, then letting it settle into a quieter position once people have
actually joined.

### 6b. Full URL plus a copy button

Currently shows `/e/<token>` — not something anyone can paste into WhatsApp.

**Why it's probably relative:** the token lives in server-rendered output, and
there's no `window.location` on the server. Whatever renders it likely had no
origin available, so it emitted the path.

Options, best first:

1. **Add `NEXT_PUBLIC_SITE_URL`** to `.env.local` and Vercel, and build the
   URL from it. Explicit, works server-side, same value everywhere.
2. **Compose it client-side** from `window.location.origin`. No config, but
   the link can't be part of the initial server render.

**Avoid `VERCEL_URL`.** It resolves to the per-deployment hostname, not your
production alias — so preview builds hand out links to a deployment that will
be superseded. It looks correct in testing and quietly rots.

Then: a **copy button** with visible confirmation. `navigator.clipboard` needs
a secure context, which HTTPS and localhost both satisfy, so that's fine — but
give it a "Copied" state rather than a silent success, and keep the URL itself
selectable as a fallback.

**Worth adding on mobile:** `navigator.share()` opens the native share sheet,
which on a phone means WhatsApp/Telegram in one tap instead of copy-then-
switch-app. This is a PWA people will use on their phones to jio colleagues,
so it fits. Feature-detect and fall back to the copy button on desktop.

### 6c. Same fix probably applies to kaki invites

`src/app/k/[token]/` is the identical pattern for joining a kaki group. If the
Jio link is relative, that one very likely is too. Check both, fix once with a
shared helper.

## 7. Saved / starred list on Places

**Start here: you already have most of this.** Wishlist exists — migration
`008_wishlist.sql`, `api/wishlist/route.ts`, a `wishlist` feature flag, and
`wishlistBoost` at weight **2.0** in the scoring config (raised from 1.0 when
`recoBoost` was removed). It is exactly "places I want to go," and it already
feeds recommendations.

So the gap is **surfacing**, not building.

**Finding (31 Jul): there is no wishlist page.** A full recursive listing of
`src/app` shows routes for admin, auth, e, events, k, kakis, login, map,
places, profile, suggest and welcome — and **no `/wishlist`**. The API route
exists (`api/wishlist/route.ts`), migration 008 exists, and the scoring weight
is live, but nothing in the route tree renders a saved list.

Its only presence is presumably an inline save control on `places/[id]`
and/or a section inside `/profile` (13.7 KB, large enough to hide one).
Unverified — `src/components` wasn't listed — but no route means no
destination.

**Two consequences worth naming:**

1. **The strongest personalization lever in the app is invisible.**
   `wishlistBoost` at 2.0 ties cuisine affinity for the highest weight in the
   engine — and unlike affinity, which is learned passively, this is the one
   users control directly. Hiding it means the main way someone can steer
   their own recommendations is a control they'll never find.
2. **The lobang → wishlist loop is broken.** The documented bridge action on a
   received lobang is one-tap "Add to Wishlist" (deliberately chosen over
   auto-adding). If there's no wishlist view, the user taps it and the place
   disappears. That's a dead end in a flow that was designed carefully.

### 7a. Two intents, and they are not the same

- **Want to go** — aspirational, somewhere you haven't been. This is Wishlist.
- **Favourites** — somewhere you already love and return to.

Worth deciding whether the second needs to exist explicitly, because **it may
already be implicit**. The engine learns cuisine affinity from what you rate
(weight 2.0) and computes a Bayesian personal rating (1.5). A place you rate
highly and revisit *is* a favourite as far as ranking is concerned.

An explicit favourites flag would be a second signal for something already
measured — with the downside that the user has to maintain it by hand, and it
goes stale silently when their taste moves.

**Recommendation:** one list, not two tables. If you do want the distinction
visible, add a `kind` column (`want_to_go` | `favourite`) to the existing
wishlist rather than a parallel structure. The wishlist already carries a
`source` field (`'lobang'` provenance from the lobang → wishlist action), so
it's used to being more than a bare join table.

### 7b. Don't add a new scoring weight without rebalancing

`recommendConfig.ts` was just rebalanced — `recoBoost`'s 1.0 was folded into
`wishlistBoost`, taking it to 2.0. Dropping a fresh `favouriteBoost` on top of
that, alongside cuisine affinity (2.0) and Bayesian rating (1.5), would
double-count the same underlying preference and quietly distort ranking.

If favourites become a real distinct kind, split the existing 2.0 between the
two kinds rather than adding to the total. Whatever you choose, update the
README's scoring table in the same commit — it is *already* wrong about these
weights.

### 7c. Give it a home — where?

The new nav (§2) is Home · Jios · Kaki · Places · Map · You. Six slots, all
spoken for, so the wishlist lives *inside* one of them:

1. **Segmented control on `/places`** — All / Saved. Most discoverable, and it
   sits where people already browse. **Preferred.**
2. **A section under You** — saved lists are personal data and `/profile` is
   becoming the You tab. Discoverable enough if the count is shown, but it's a
   destination people visit rarely.
3. **A strip on Home** — "Your saved places" above the fold. Works *alongside*
   either of the above rather than instead of them; Home is where a hungry
   person starts.

**Watch the load on `/places`.** It already has search, cuisine/budget/walk
filters, walk-time sort and Load More, and is gaining a Suggest button (§2).
Adding a Saved view makes it the busiest screen in the app. That argues for a
proper segmented control at the top — one clear axis — rather than another
control in a growing row.

**Whatever you pick, add the save control to every place surface**: the
`/places` list card, `/places/[id]`, and the `/suggest` result cards. Saving is
worth almost nothing if it's only reachable from the detail page.

Also give the lobang inbox's "Add to Wishlist" action somewhere to land —
ideally a confirmation that links straight to the saved list.

### 7d. Group favourites already exist

Kakis have shared stats including group favourites. Worth checking what's
already there before building anything group-facing — and worth a link from a
personal saved list to the group equivalent.

## 8. Edit (and delete) your own reviews

**The database is already built for this.** Migration 021's trigger recomputes
`places.avg_rating` and `visit_count` on `visits` **insert, update *and*
delete** — the update and delete paths were written deliberately, for exactly
this. Aggregates will stay correct the moment an edit endpoint exists.

**What's missing is the API surface.** `api/visits/route.ts` exists with no
`api/visits/[id]/` beside it, so there's no per-row update or delete route.
That matches the symptom.

### 8a. Closes a known gap

`CHANGELOG_20260729.md` lists an open question against the ratings trigger:
*add a test case confirming rating edits/deletes recompute correctly, not just
inserts.* Untestable today because nothing can edit a visit. Building this
makes that test both possible and mandatory — write it as part of the feature,
not after.

### 8b. Decide what "a review" is, first

A visit row appears to carry rating, optional review text, a date, and a
private/shared distinction ("log a visit privately, or share it as a review").
So "edit my review" could mean four different things:

- Change the **rating** — recomputes place aggregates via the trigger
- Change the **text**
- Change **visibility** — un-share a shared review back to private, which is
  a genuinely useful thing to want and easy to overlook
- Change the **date** — affects metrics, see 8d

**And there may be several.** If each visit is an occasion, you have many
visits to a favourite place, each with its own rating. "Your review" is then
ambiguous. Resolve this before designing the UI: is the edit target a specific
visit, or a single current opinion per place? The profile list wants the
former; a place page saying "your review" implies the latter.

### 8c. Deletion needs its own decision

Deleting a visit is not symmetrical with editing it — it removes history.
Note that the app's stance elsewhere is explicitly **never hard-delete**:
places are blocked, not deleted, to avoid foreign-key trouble. Visits have no
dependants, so a real delete is safer here, but the inconsistency is worth
being deliberate about rather than accidental.

### 8d. Watch the downstream

- **Metrics.** `metrics.ts` computes cuisine streaks and "what you actually
  eat versus what you think you eat" from visits. Editing a date or a place
  rewrites history retroactively — a streak that existed yesterday can vanish.
  Acceptable, but don't be surprised by it.
- **Recommendations.** Cuisine affinity is learned from ratings, so an edit
  legitimately changes future suggestions. That's the feature working.
- **Shared reviews others have already read.** Silent mutation is slightly
  off. A lightweight `updated_at` rendered as "edited" is probably enough for
  a trusted team — full revision history is not warranted.

### 8e. RLS

Check `007_rls.sql` (and 004) for whether `visits` has owner-scoped **UPDATE**
and **DELETE** policies, or only INSERT/SELECT. Writes are owner-scoped
throughout the schema, so the pattern exists — but a policy that was never
needed may never have been written.

Make sure an update can't reassign `user_id` or `place_id` to something the
caller doesn't own. The `places.status` precedent — a column-level `GRANT`
excluding the column that matters — is the in-repo pattern if a blunt policy
isn't tight enough.

### 8f. Where it goes

Both surfaces the request names, sharing one component:

- **`places/[id]`** — your own visit(s) shown inline with an edit affordance
- **`/profile`** — a list of your visits/reviews, each editable

The profile list is the more important of the two: it's the only place someone
can find a review of a place they can't currently remember the name of.

## 9. Let any signed-in user edit place details

**Check first — this may already be true.** `CHANGELOG_20260729.md` records
that `updatePlace()` / `PUT /api/places/[id]` previously had *no* permission
check at all, and the 30 Jul fix deliberately locked down **only `status`**
(specifically to/from `archived`), leaving every other field editable by any
signed-in user. There's a column-level `GRANT UPDATE` on `places` that excludes
`status` precisely so the rest stays open.

So the API probably already permits this. Read `api/places/[id]/route.ts`
(touched 30 Jul) to confirm. If it does, **the gap is UI** — `places/[id]`
likely has no edit affordance, and `places/new` exists only for creating.

### 9a. What must stay locked

Do not loosen these while opening the rest:

- **`status` → `blocked`** — creator or admin only, with a reason, via the
  `block_place` SECURITY DEFINER function. Unblock is admin-only.
- **`status` → `archived`** — admin only. This was an explicit requirement.
- **`review_place`** (`needs_review` → `active`/`blocked`) is *already* open to
  any signed-in user by design — crowd-confirmation of OSM data quality. No
  change needed.

The rule that falls out: **anyone can correct a place; only admins can make one
disappear.** That's a coherent line, and the schema is already most of the way
to it.

### 9b. Editing coordinates invalidates `walk_cache`

**The real bug hiding in this feature.** If a user corrects a place's lat/lng,
its cached walk time is instantly wrong — the same staleness problem as §1, but
arriving one row at a time with nobody watching.

Delete that place's `walk_cache` row whenever its coordinates change. A trigger
is the reliable way (same reasoning as §1e), and it means the place sorts last
under `NULLS LAST` until re-enriched — honest rather than confidently wrong.

Editing **cuisine** likewise changes recommendation behaviour: affinity scoring
and the "cuisines I'd rather not eat" exclusions both key off it. Correct
behaviour, but not a cosmetic field.

### 9c. Add minimal attribution

`place_moderation_log` records block/unblock only. General edits would leave no
trail — if someone garbles a name or drags a pin, there's no record of who,
when, or what it was before.

An `updated_by` / `updated_at` pair on `places` is cheap and enough for a
trusted team. Full revision history isn't warranted yet; being able to ask "who
last touched this" is.

### 9d. Decide how this relates to flagging

Migration 022's flag → admin-review flow exists for bad place data. Open
editing partially routes around it — which is arguably the point.

They coexist cleanly if the split is: **edit what you can fix** (wrong cuisine,
wrong budget, typo), **flag what you can't** (permanently closed, duplicate,
inappropriate). The flag `resolution` enum already includes `edited`, so the
admin flow anticipates edits as an outcome.

Worth making that split visible in the UI copy, or people will flag things they
could have fixed themselves in five seconds.

### 9e. One form, two modes

Edit reuses the **same form as create** — `places/new/page.tsx` — rather than a
separate cut-down editor. Extract it into a shared `PlaceForm` component taking
a mode (`create` | `edit`) and initial values; `places/new` renders it empty,
the edit route renders it prefilled.

**Editable:** name, cuisine(s), budget tier, type/category, location, and
anything else the create form already collects. If it can be set at creation it
can be corrected later — that's the whole point.

**Cuisine is multi-valued.** The engine excludes a place only when *every* one
of its cuisines is on your "rather not eat" list, so the field is a set, not a
single value. The edit control needs to be the same multi-select, not a
degraded single picker.

**Location wants the geocode path, not raw lat/lng boxes.**
`api/geocode/route.ts` exists and `places/new` presumably already uses it —
address in, coordinates out. Edit should go through the same route so a
corrected address produces properly geocoded coordinates rather than a
hand-typed pair. A map pin drag is the natural complement.

**Keep derived fields out of the form entirely:** `walk_minutes`,
`avg_rating`, `visit_count`, `rating_updated_at`, `has_pending_flag`, `status`.
These are computed or gated, and a form that renders them invites someone to
try. Sharing a component makes this easy to get wrong — the create form never
had to think about them because they didn't exist yet at creation time.

**Share the validation too.** If create requires a field, edit must require it
identically, or a place can be saved into a state creation would have rejected.

### 9f. Will the discovery cron overwrite manual edits?

**Worth verifying before shipping this.** Places found via Overpass carry OSM
provenance, and `discovery.ts` handles normalisation and dedupe. If the daily
cron ever *updates* existing rows rather than only inserting new ones, a user's
careful correction gets silently reverted overnight — the worst kind of bug,
because it looks like the edit never saved.

The README's sample cron output (`{"fetched":45,"new":3,"skipped":42}`)
suggests it skips existing places rather than updating them, which would make
edits safe. Confirm that's actually what the code does. If dedupe ever grows an
"update existing" path, manual edits need protecting — an `edited_by_user`
flag that discovery refuses to overwrite is the usual answer.

### 9g. Smaller notes

- **Last write wins.** No optimistic concurrency, so two simultaneous editors
  silently clobber each other. Fine at team scale; worth remembering.
- **Guard the immutable fields.** An update must not reassign `id`,
  `office_id` or `created_by`.
- **Revisit at scale.** This is a wiki-style trust model — right for one
  trusted office, wrong for a public product. The natural escalation is the
  same `email`-mode identity gate described in `docs/user-discovery.md`.

## Suggested order

Several of these turned out to be much smaller than they first looked. Do the
cheap high-impact ones first and re-assess.

1. **§1 office location** — highest impact, smallest change, and it's currently
   corrupting recommendation output. Do it first.
2. **§3 Home's Start a Jio** — possibly a one-line link fix. Cheap to test,
   and it closes the option-search and date+time gaps in one move.
3. **§5 double name prompt** — check the `onboarded_at` theory first; if it
   holds this is minutes, not hours, and it's the first thing every new user
   hits.
4. **§6 share link** — small, self-contained, and it's blocking the one thing
   a Jio exists to do. The full-URL fix is likely one env var plus a helper.
5. **§4 the invite picker** — the biggest build. Do it after §3, so you're
   extracting the component from a flow Home already shares, and after §4b's
   question about what "link a kaki" means is settled.
6. **§7 saved list** — likely surfacing-only if Wishlist already works, and
   the broken lobang → wishlist loop makes it more urgent than it looks.
7. **§8 edit reviews** — DB already supports it; needs an endpoint, an RLS
   check, and the trigger test that's been open since migration 021.
8. **§9 open place editing** — check whether the API already allows it; if so
   this is a UI affordance plus the `walk_cache` trigger from 9b.
9. **§2 bottom nav** — do last, once the Suggest-into-Places question is
   actually decided.

Items 1–3 are all "verify a hypothesis, then make a small change." Worth
running through all three before starting anything larger, since each could
close in minutes and §3 in particular determines what §4 is building on.

**§4 and §6 are the two that matter most for whether people actually use
this** — one is how you get people into a Jio, the other is how you tell them
it exists. Both are currently harder than they need to be.
